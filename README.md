# Enterprise PKI Web Enrollment Portal (AD CS Modern Gateway)

Modern web portal built with **HTML5** and **ASP.NET Core 8 (C#)**, designed to replace the obsolete and deprecated **Microsoft Web Enrollment (`certsrv`)**, eliminating any dependency on ActiveX/Internet Explorer and mitigating the security risks associated with NTLM Relay (ESC8).

---

## 🌟 Key Features

1. **Client-Side Key Generation (HTML5 Web Crypto)**:

   * The key pair (RSA 2048/3072/4096 or ECC) is generated in memory directly inside the browser (`window.crypto.subtle`).
   * The **private key never travels over the network and never touches the server**.
   * When AD CS issues the certificate, the browser generates a password-encrypted **PKCS#12 (.pfx)** package using a password chosen by the user, ready to be installed on Windows/IIS.
2. **Existing CSR Upload (Base64 / File)**:

   * Support for externally generated `.csr` / `.req` files, such as those generated by Linux servers, firewalls, switches, and network appliances.
   * Instant parsing and inspection of CSR fields (Subject, SAN, algorithm, key size) before submission.
3. **Hybrid Architecture for Untrusted Forests**:

   * **Standalone Mode (Co-located with MSCS)**: Installed locally within each forest, communicating with the local Sub-CA without requiring any cross-forest firewall changes.
   * **Multi-CA Hub Mode (Internal DMZ)**: A single portal exposed in the DMZ, allowing users to select the correct target CA from a drop-down menu.
4. **Native Microsoft AD CS Integration**:

   * High-performance connectivity through the Microsoft COM interface `CCertRequest` (`CertificateAuthority.Request` from `certcli.dll`).
   * Automatic fallback to the `certreq.exe` CLI.
   * Built-in simulator for development, testing, and offline environments, enabled with `"UseSimulator": true`.
5. **Secure Certificate Retrieval (Pending or Issued)**:

   * Allows users to retrieve an issued certificate by entering the *Request ID* or by viewing their own *“Your Certificates”* table.
   * **Ownership and security checks**: Downloads are allowed exclusively for the Windows user who submitted the original request (`ctx.User.Identity.Name`) or for administrators, preventing unauthorized access to other users’ certificates (`HTTP 403 Forbidden`).
6. **Manual Approval Workflow (Hold & Review)**:

   * Ability to enable `RequiresApproval: true` on sensitive templates.
   * Issued certificates are securely intercepted, stored in `held-requests.json` in `PendingApproval` state, and released only upon administrator authorization.
7. **Role-Based Access Control (Template RBAC)**:

   * Granular assignment of certificate templates to specific Active Directory groups (`AllowedGroups`). Users outside authorized groups are restricted from issuing certificates with those templates.
8. **Multi-Language UI & Theme Support**:

   * Full support for 5 languages (**English, Italian, French, German, Spanish**) with real-time dynamic switching.
   * Persistent Light and Dark theme selection.
9. **REST API for Automation (win-acme / PowerShell)**:

   * Exposes RESTful endpoints for integrating automatic renewal scripts and automation clients such as `win-acme`.

## 🖥️ IIS Installation (Alongside certsrv)

The `Install-PkiPortal.ps1` script installs the portal as a **separate IIS website** on the same server where Microsoft Web Enrollment (`certsrv`) is running, **without modifying or interrupting certsrv**.

### What the installation script does

1. Verifies and installs the required IIS features without modifying those used by certsrv.
2. Verifies and installs the .NET 8 ASP.NET Core Hosting Bundle.
3. Builds and publishes the application to the destination directory.
4. Creates a **dedicated Application Pool**, separate from `DefaultAppPool`/certsrv.
5. Creates a **new IIS website** on a configurable port and hostname.
6. Configures file-system permissions and the firewall rule.
7. Verifies that certsrv remains unchanged and operational.

### Prerequisites

* Windows Server 2016 or later with the IIS role installed.
* Local administrator privileges.
* .NET 8 SDK for compilation, or the .NET 8 Hosting Bundle for runtime-only installations.

### Installation examples

```powershell
# Basic installation: HTTP site on port 8443
.\\Install-PkiPortal.ps1

# Installation with a gMSA (Group Managed Service Account — no password required)
.\\Install-PkiPortal.ps1 -SitePort 8443 -AppPoolIdentity "DOMAIN\\GMA$" -IsGMSA

# HTTPS installation with a custom hostname and standard user account
.\\Install-PkiPortal.ps1 -SitePort 443 `
    -SiteHostHeader "pki.company.lan" `
    -UseHttps `
    -CertThumbprint "A1B2C3D4E5F6..." `
    -AppPoolIdentity "DOMAIN\\svc-pki-portal" `
    -AppPoolPassword (Read-Host -AsSecureString "Password")

# Installation on a custom port with a custom site name
.\\Install-PkiPortal.ps1 -SiteName "PKI-Enrollment-F1" -SitePort 9443

# Installation without a firewall rule (centrally managed environments)
.\\Install-PkiPortal.ps1 -SitePort 8443 -SkipFirewall
```

### Available parameters

|Parameter|Default|Description|
|-|-|-|
|`-SiteName`|`PkiWebEnrollment`|IIS site name|
|`-SitePort`|`8443`|Listening TCP port|
|`-SiteHostHeader`|*(empty = all)*|Specific hostname, e.g. `pki.company.lan`|
|`-InstallPath`|`C:\\inetpub\\PkiWebEnrollment`|Publishing directory|
|`-AppPoolIdentity`|`ApplicationPoolIdentity`|Pool identity (`NetworkService`, `LocalSystem`, `DOMAIN\\Account$`, or `DOMAIN\\User`)|
|`-AppPoolPassword`|*(none)*|Password for a standard domain user account, not required for a gMSA|
|`-IsGMSA`|*(no)*|Specifies that the identity is a gMSA, without a password; appends `$` if missing|
|`-UseHttps`|*(no)*|Enables the HTTPS binding|
|`-CertThumbprint`|*(none)*|SSL certificate thumbprint|
|`-SourcePath`|*(current directory)*|Source project path|
|`-SkipDotnetPublish`|*(no)*|Skips compilation and uses already-published files|
|`-SkipFirewall`|*(no)*|Does not create the firewall rule|

### Uninstallation

```powershell
# Removes the IIS site, application pool, and firewall rule; preserves the files
.\Uninstall-PkiPortal.ps1

# Removes everything, including application files
.\Uninstall-PkiPortal.ps1 -RemoveFiles
```

> **⚠️ Non-intrusiveness guarantee**: Both scripts operate exclusively on the dedicated
> PKI portal website and application pool. The `Default Web Site` and the
> `/CertSrv` application are **never touched or modified**.

Edit the `appsettings.json` file in the installation directory, for example:

```text
C:\\inetpub\\PkiWebEnrollment\\appsettings.json
```

### 1\. Local Mode (Installation alongside certsrv in the same forest)

In this mode, no credential configuration is required: the portal uses the IIS Application Pool identity (`AuthMode: "LocalIdentity"`).

```json
{
  "PortalConfig": {
    "PortalMode": "Standalone",
    "PortalTitle": "Enterprise PKI Web Enrollment Portal",
    "DefaultCaId": "ca-forest1",
    "CAs": [
      {
        "Id": "ca-forest1",
        "DisplayName": "Forest 1 - Enterprise Issuing CA (Prod)",
        "ForestOrDomain": "forest1.lan",
        "ConfigString": "subca01.forest1.lan\\Forest1-SubCA",
        "IsDefault": true,
        "UseSimulator": false,
        "AuthMode": "LocalIdentity",
        "Templates": [ ... ]
      }
    ]
  }
}
```

### 2\. Centralized Hub Mode (Internal DMZ toward multiple untrusted forests)

In this mode, the portal contacts each Sub-CA using the specific service account for that forest, stored in **Windows Credential Manager** (**no password is stored in the configuration files**):

```json
{
  "PortalConfig": {
    "PortalMode": "Hub",
    "PortalTitle": "Enterprise PKI Web Enrollment Portal",
    "DefaultCaId": "ca-forest1",
    "CAs": [
      {
        "Id": "ca-forest1",
        "DisplayName": "Forest 1 - Enterprise Issuing CA",
        "ForestOrDomain": "forest1.lan",
        "ConfigString": "subca01.forest1.lan\\Forest1-SubCA",
        "IsDefault": true,
        "UseSimulator": false,
        "AuthMode": "CredentialManager",
        "CredentialTarget": "subca01.forest1.lan",
        "Templates": [ ... ]
      },
      {
        "Id": "ca-forest2",
        "DisplayName": "Forest 2 - Enterprise Issuing CA (Untrusted)",
        "ForestOrDomain": "forest2.lan",
        "ConfigString": "subca02.forest2.lan\\Forest2-SubCA",
        "IsDefault": false,
        "UseSimulator": false,
        "AuthMode": "CredentialManager",
        "CredentialTarget": "subca02.forest2.lan",
        "Templates": [ ... ]
      }
    ]
  }
}
```

## 🔐 Secure Credential Registration (Windows Credential Manager)

To register service-account credentials for the different forests **without ever writing passwords in plain text**, use the included `Add-CaCredential.ps1` script:

```powershell
# Registers the account for the Forest 1 Sub-CA; the password is requested using a protected prompt
.\Add-CaCredential.ps1 -Target "subca01.forest1.lan" -UserName "FOREST1\\svc-pki-enroll"

# Registers the account for the Forest 2 Sub-CA (separate untrusted forest)
.\Add-CaCredential.ps1 -Target "subca02.forest2.lan" -UserName "FOREST2\\svc-pki-enroll"

# Lists the targets registered in Credential Manager
.\Add-CaCredential.ps1 -List

# Removes a stored credential
.\Add-CaCredential.ps1 -Target "subca02.forest2.lan" -Remove
```

> **How it works under the hood**:
> When a request arrives for `ca-forest2`, the backend queries `Advapi32.dll` (`CredReadW`) for the `subca02.forest2.lan` target, creates a secure network token through `LogonUser` (`LOGON32\_LOGON\_NEW\_CREDENTIALS`), and executes the operation (`CCertRequest` / `certreq`) inside a `WindowsIdentity.RunImpersonated` block. RPC/DCOM calls to the remote CA therefore use the account from that forest, overcoming the absence of a trust relationship.

## 🔒 Security and Best Practices

* **HTTPS**: Always use HTTPS in production. The installation script supports the `-UseHttps -CertThumbprint` parameters.
* **Service Account**: The IIS Application Pool must run under an account that has *Request Certificates* (Enroll) permissions on the desired AD CS templates. For Standalone Mode within the forest, `NetworkService` or a Managed Service Account is sufficient.
* **ESC8 Hardening**: This portal does not expose the traditional `certsrv` endpoint. **Important note:** the default installation responds over plain HTTP with Windows Authentication (NTLM may be negotiated in cleartext across the network, creating a relay risk), and the installation script now requires explicit confirmation for the HTTP path. In production, **always** install with `-UseHttps -CertThumbprint` and enable Extended Protection for Authentication (EPA/EPAL) to mitigate relay attacks.
* **Separation from certsrv**: The portal uses a completely separate IIS website and Application Pool, ensuring that an issue with the portal does not affect certsrv, and vice versa.

## 🛡️ Administrative panel and approval workflow

The portal includes `/admin.html`, protected by Windows Authentication and an authorization ACL configured in the `AdminConfig` section of `appsettings.json`. Access can be granted to groups through `AllowedGroups` or to individual accounts through `AllowedUsers`. Any other user receives `HTTP 403 Forbidden` when accessing the administrative page or `/api/admin/*` endpoints.

```json
{
  "AdminConfig": {
    "AllowedGroups": [
      "BUILTIN\\Administrators",
      "CONTOSO\\Domain Admins"
    ],
    "AllowedUsers": [
      "CONTOSO\\user-adm"
    ]
  }
}
```

### Manual approval workflow

When a certificate template has `RequiresApproval: true`:

1. The user submits a certificate request through Web Crypto or an existing CSR.
2. AD CS processes the request and technically issues the certificate.
3. The portal intercepts the issued certificate, stores it in `held-requests.json`, and marks the request as `PendingApproval`.
4. The user receives a unique Hold ID and is informed that the request is awaiting administrator approval.
5. The certificate cannot be downloaded until an authorized administrator approves it.

After approval, the certificate becomes available to the original requester through the certificate retrieval section. Administrators can also reject a request and optionally record a reason.

### Hold request states

|State|Description|Available action|
|-|-|-|
|`PendingApproval`|Certificate held pending administrator authorization.|Approve and release, or reject.|
|`Approved`|Request approved by an administrator.|Certificate download is enabled for the requester.|
|`Issued`|Certificate issued directly without portal approval.|Certificate can be retrieved.|
|`UnderSubmission`|Request is pending approval directly in AD CS.|View request details.|
|`Rejected`|Request rejected by an administrator.|View rejection reason.|

### Administrative features

* **Certificate requests**: filter by status and view Hold ID, submission date, requester, template, CN, SAN, target CA, AD CS Request ID, notes, review information, and rejection reason.
* **Portal and CA configuration**: manage portal title, Standalone or Hub mode, default CA, CA connections, authentication mode, credential targets, templates, allowed key types, validity, key usages, and manual approval settings.
* **Template discovery**: use “Discover from CA” to query published templates through DCOM or `certutil`.
* **Hot reload**: saving the configuration updates the files and reloads the in-memory provider without restarting the IIS Application Pool.

### Administrative REST endpoints

|Method|Endpoint|Description|Permission|
|-|-|-|-|
|GET|`/api/admin/check`|Checks whether the current user is a portal administrator.|Authenticated user|
|GET|`/api/admin/config`|Returns the complete portal configuration.|Administrator|
|PUT|`/api/admin/config`|Saves the configuration and reloads it in memory.|Administrator|
|POST|`/api/admin/templates/discover`|Queries a CA for published certificate templates.|Administrator|
|GET|`/api/admin/held-requests?status={filter}`|Lists held requests: `pending`, `approved`, `rejected`, or `all`.|Administrator|
|GET|`/api/admin/held-requests/{holdId}`|Returns the details of a held request and its archived certificate.|Administrator|
|POST|`/api/admin/held-requests/{holdId}/approve`|Approves the request and authorizes certificate release.|Administrator|
|POST|`/api/admin/held-requests/{holdId}/reject`|Rejects the request, optionally recording a reason.|Administrator|

## 🔎 Template discovery and validity

The “Discover from CA” function reads the template definition from Active Directory and retrieves the `pKIDefaultLifetime` attribute. The value is converted from 100-nanosecond units to days, saved in `appsettings.json`, and shown as read-only information in the administration interface.

In Hub mode, the LDAP query uses the credentials configured for the destination forest. If Active Directory is unavailable, the portal falls back to:

```powershell
certutil -config "server\\CA" -template TemplateName
```

For simulator CAs, validity is taken from the mock template definitions.
